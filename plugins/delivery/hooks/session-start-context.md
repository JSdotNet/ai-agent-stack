In a repository that has adopted the delivery engine, route every change through one of two flow-* skills: any change to a devbook folder — an arc42/ chapter, decision record, debt record, or proposal, the domain model in domain/, the technology graph in tech/, design guidelines in design/, the AI adoption record in ai/ -> flow-spec (it stops and says so when the repository has not adopted the folder, and loads the repository's own instruction files for the folder rather than carrying rules of its own); every other change to the repository -> flow-code, which derives the kind in its first stage and runs one tier for every kind — feature work, a bug fix, a structure or layout refactor, a new module, service, or MVP, tooling, CI, scripting, documentation outside the devbook folders, housekeeping, a dependency, package, or framework move such as an Aspire upgrade, and creating, governing, or scaffolding a repository. A task that changes nothing in the repository needs no flow. There is no fallback flow: a matching skill whose preconditions are unmet is run anyway and derives what is missing in its first stage. This list is the plugin-provided baseline, not an exhaustive catalog: a repository may provide additional repo-native flow-* skills in the host's own skill folder, and those take precedence for the changes they cover. If you decide not to use a flow skill for a change, say so explicitly and give the reason before continuing. A flow is one session and never spawns another; a backlog worked with nobody watching is a higher layer's issue sweep, one item at a time in its own session. Every flow reports progress to every bound delivery surface, resolved by pattern from the live tool list rather than by a hardcoded tool prefix, and no surface bound is a normal outcome that never blocks a stage. A repository declares its bindings, phases — one complete map per flow — policy, and gates in .devbook/config.json; configuration chooses among behaviour the engine already implements and never adds a stage. Configuration may add human gates anywhere; it may never remove the Personal Validation gate or hand a gate to a plugin. A model or an effort in .devbook/config.json is a team default, and every personal overlay wins over it field by field. A repository declares how its application is set up and starts, and where, in its own run recipe at .claude/skills/run-<name>/SKILL.md — recorded by /run-skill-generator, followed by Claude Code's run skill, reached from Copilot through .github/skills/run — and a flow starts the app by invoking run; and its QA depth in policy; nothing to start is phase-verify's app set to null. The repository's own MCP configuration and instruction files remain the source of truth for MCP servers. Everything personal to a machine — QA depth inside the repository's ceiling, a local binding, a phase's model or effort, what a layered plugin remembers under its own ext.<plugin> key — lives in a stack-config overlay under the user's devbook config directory, never in the repository; read the effective configuration by running this plugin's `tools/stack-config/check.mjs --print` from the repository root (the script resolves .devbook/config.json against the working directory, so a run from the plugin's folder prints defaults) and never merge a layer by hand, and offer devbook-config:local when that output shows no overlay present.
